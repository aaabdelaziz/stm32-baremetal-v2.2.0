# 9-CAN — Bare-Metal bxCAN Send and Receive

This guide introduces the CAN concepts used by this example before walking through the firmware. The project uses CMSIS register definitions to configure the STM32F091 bxCAN peripheral, periodically transmit one classic CAN frame, and poll for frames received from other nodes. USART2 prints transmit and receive status to a serial terminal.

## 1. CAN basics for this example

### A controller needs a transceiver

The STM32F091 contains a CAN controller, called **bxCAN**. The controller creates and checks CAN frames, but its pins are logic-level `CAN_TX` and `CAN_RX` signals. A separate CAN transceiver converts those logic signals to the differential bus pair `CANH` and `CANL`, and converts the bus signal back to logic levels for the MCU.

Connect MCU `CAN_TX` to transceiver `TXD`, and MCU `CAN_RX` to transceiver `RXD`. Connect the transceiver’s `CANH` and `CANL` to the matching bus wires. Do not connect PA11 or PA12 directly to CANH/CANL.

### The bus is shared and multi-master

Any node can start transmitting when the bus is idle. CAN uses two bus states:

- **Recessive** represents a logical 1. When no node drives a dominant bit, the bus is recessive.
- **Dominant** represents a logical 0. A dominant bit overrides a recessive bit when nodes transmit at the same time.

Nodes that begin together compare their identifier bits while transmitting. If a node sends recessive but observes dominant, it stops transmitting and retries later. This is **non-destructive arbitration**: the winning frame continues without being corrupted. For standard 11-bit identifiers, a numerically lower identifier has higher arbitration priority because it produces dominant bits earlier. The identifier describes the frame’s meaning/priority; it is not a destination address.

This application submits one frame at a time through bxCAN transmit mailbox 0. bxCAN waits for an idle bus and performs the actual arbitration on the wire. This application does not implement arbitration in software. If another node transmits at the same time, the bus resolves the competition according to the identifier bits.

### What is in a frame

This project periodically sends a **classic CAN 2.0 standard data frame**:

| Field | This example | Meaning |
| --- | --- | --- |
| Identifier | `0x123` | 11-bit frame identifier and arbitration priority |
| IDE | 0 | Standard, 11-bit identifier (not extended 29-bit) |
| RTR | 0 | Data frame (not a remote request) |
| DLC | 8 | Eight payload bytes follow |
| Data | `CA 4E 00 01 DE AD BE EF` | Application-defined payload |
| CRC / ACK | Generated by bxCAN | Frame integrity and receiver acknowledgement |

CAN’s ACK slot is a bus-level acknowledgement: at least one correctly receiving node drives the ACK bit dominant. The transmitting node does not acknowledge its own frame. Therefore, successful transmission in this normal-mode demo requires a second active node configured for the same bitrate. A CAN analyzer in listen-only/silent mode can observe frames but usually does not acknowledge them.

For reception, bxCAN first checks each valid frame against its acceptance filters. A matching frame is placed in an RX FIFO until firmware reads and releases it. This example configures a catch-all filter, so it accepts standard and extended identifiers into FIFO0. The receive code reports remote frames as such; remote frames contain no payload bytes.

### Bitrate and termination

Every node on a CAN bus must use compatible bit timing. This project uses an 8 MHz APB1 clock and 125 kbit/s CAN timing. The two ends of a physical high-speed CAN bus are normally terminated with 120 Ω each, from CANH to CANL. Use a short linear bus with the terminators at its physical ends; avoid adding extra terminators at intermediate nodes.

## 2. Hardware and configuration used here

```text
Board:          NUCLEO-F091RC
MCU:            STM32F091RCTx, Cortex-M0
System/APB1:    8 MHz HSI, APB1 undivided
CAN peripheral: bxCAN1, normal mode, 125 kbit/s, polling RX FIFO0
CAN_RX:         PA11, alternate function 4
CAN_TX:         PA12, alternate function 4
Frame:          standard ID 0x123, DLC 8
Payload:        CA 4E 00 01 DE AD BE EF
UART status:    USART2, PA2 TX, 9600 baud, 8-N-1
```

On the NUCLEO-F091RC, PA11 and PA12 are exposed at CN10 pins 14 and 12 respectively. The board does not turn these MCU logic signals into CANH/CANL; use an external transceiver unless your attached CAN hardware already includes one.

Example wiring:

```text
NUCLEO PA12 (CAN_TX) ───── transceiver TXD
NUCLEO PA11 (CAN_RX) ───── transceiver RXD
NUCLEO GND            ───── transceiver GND
transceiver CANH       ───── CAN bus CANH ───── other node CANH
transceiver CANL       ───── CAN bus CANL ───── other node CANL
```

Use a transceiver compatible with the MCU’s 3.3 V logic levels. Ensure the bus and the second node share a suitable ground reference and that the bus has the correct end termination.

## 3. CMSIS and project structure

This is a register-level CMSIS project. `#include "stm32f0xx.h"` selects the STM32F091 definitions using the existing `STM32F091xC` compiler symbol. It provides the `CAN_TypeDef` register layout and `CAN` peripheral pointer, along with RCC and GPIO definitions.

`CAN_HandleTypeDef` is an STM32 HAL type, not a CMSIS type. This firmware does not use HAL and does not need `stm32f0xx_hal.h`; the CAN code accesses registers such as `CAN->MCR`, `CAN->BTR`, and `CAN->sTxMailBox[0]` directly.

```text
Inc/can.h             CAN initialization/send/receive API and frame types
Inc/clock_config.h    Shared MCU/APB1 clock and UART baud settings
Inc/uart.h            USART2 API
Src/can.c             GPIO, clock, filters, bit timing, TX/RX mailbox logic
Src/main.c            Periodic sender, RX polling/display, UART status
Src/uart.c            Blocking USART2 driver used for status output
Startup/              Cortex-M0 startup and interrupt vector table
STM32F091RCTX_FLASH.ld Flash and RAM layout
```

The project’s CubeIDE compiler settings already include the shared CMSIS core and STM32F0 device header folders and define `STM32F091xC`. `Inc/clock_config.h` records the assumed 8 MHz system/APB1 clock. If the clock tree changes, update that configuration and recalculate the CAN BTR fields in `Src/can.c`; the bitrate must match the other bus nodes.

## 4. How the firmware initializes CAN

The sequence is implemented in `can1_init()` in `Src/can.c`:

1. **Enable clocks.** Enable GPIOA on AHB and CAN1 on APB1 before accessing their registers.
2. **Select CAN pins.** Put PA11 and PA12 in alternate-function mode and select AF4 for `CAN_RX` and `CAN_TX`. The code also selects push-pull output, high GPIO speed, and no internal pulls.
3. **Enter bxCAN initialization mode.** Set `CAN_MCR_INRQ`, then wait until hardware sets `CAN_MSR_INAK`. Timing registers are changed only while bxCAN acknowledges initialization mode.
4. **Program bit timing.** With APB1 at 8 MHz, the code uses a prescaler of 4 and 16 time quanta per bit: `tq = 4 / 8 MHz = 0.5 µs`; `1 sync + 13 TS1 + 2 TS2 = 16 tq = 8 µs`, giving `125 kbit/s`. The sample point is `(1 sync + 13 TS1) / 16 tq = 87.5%`. The BTR register encodes prescaler and segment values minus one, so the programmed fields are BRP=3, TS1=12, and TS2=1. SJW remains at its reset value of one time quantum.
5. **Configure receive filtering.** While filter initialization mode (`FMR.FINIT`) is set, bank 0 is selected as a 32-bit identifier-mask filter and assigned to FIFO0. Both the ID value and mask are zero, so no identifier bits must match and all standard/extended frames are accepted. The filter is enabled and `FINIT` is cleared.
6. **Select one-shot transmit behavior and start CAN.** Set `CAN_MCR_NART` to disable automatic retransmission, clear `CAN_MCR_INRQ`, then wait for `CAN_MSR_INAK` to clear. If there is no ACK, one attempt reports an error and releases the mailbox instead of retrying indefinitely.

Each hardware wait has a finite loop limit. `can1_init()` reports failure if the controller does not enter or leave initialization mode before the limit expires.

## 5. How a frame is submitted and arbitrated

`can1_send()` in `Src/can.c` performs the following steps:

1. Check that the identifier fits 11 bits, the DLC is at most 8, and the data pointer is valid for a non-empty frame.
2. Check `CAN_TSR_TME0` to ensure transmit mailbox 0 is empty and writable.
3. Pack payload bytes into `TDLR` and `TDHR`, and write the DLC to `TDTR`.
4. Write `0x123` into the standard identifier field of `TIR`. IDE and RTR are left clear, selecting a standard data frame.
5. Set `TXRQ` in `TIR`. This requests transmission; the CAN controller waits until the bus is available, then sends the frame and performs bitwise arbitration with any simultaneous sender.
6. Wait for `RQCP0` to indicate mailbox completion. `TXOK0` means the frame completed successfully and was acknowledged. If `TXOK0` is clear, the function reports a transmit error. It clears the mailbox completion flag by writing one to `RQCP0`.

Because this demo uses only mailbox 0, it queues only one frame at a time. If several nodes request the bus together, arbitration is handled in hardware: the lower standard identifier wins, and losing nodes defer and retry.

### Receiving a frame

`can1_receive()` polls the FIFO0 pending count and returns immediately if no frame is waiting. For a pending frame it:

1. Copies the identifier and frame type from the RX identifier register.
2. Reads the DLC and payload words from the FIFO mailbox. Extended identifiers are reconstructed from the STID and EXID fields; standard IDs use STID alone.
3. Copies at most eight payload bytes into `can_frame_t.data`. Remote frames report their DLC but have no payload data.
4. Records a FIFO overrun flag, clears that hardware flag when set, and releases the FIFO mailbox so bxCAN can accept another frame.

The receive API is polling-based and uses no interrupts. `main()` calls it on each pass through the loop and prints received frames in hexadecimal. The loop also periodically sends the fixed eight-byte frame. UART printing and the synchronous transmit wait pause polling briefly, so this small example is intended for low-rate demonstrations rather than a high-throughput receiver.

## 6. Build and flash in STM32CubeIDE

1. Import the `9-CAN` project into an STM32CubeIDE workspace. If the shared `chip_headers` project is not already present in that workspace, import it too. Use the repository root as the import root and enable nested project search when needed.
2. Confirm that the project appears as `9-CAN` and that the `chip_headers` project is available. The configured compiler paths refer to that shared CMSIS project.
3. Select the `Debug` configuration, then choose **Project → Build Project**. The firmware sources are under `Src`; the project source entries include both `Src` and `Inc`.
4. Connect the NUCLEO-F091RC over USB. In Project Explorer, select `9-CAN` and launch **Debug As → STM32 Cortex-M C/C++ Application**, or use the included `9-CAN.launch` configuration. Start/resume execution to run the main loop.
5. Open a serial terminal on the ST-LINK virtual COM port with **9600 baud, 8 data bits, no parity, 1 stop bit**. USART2 PA2 is the status TX pin; PA3 RX is configured but not used by this demo.
6. Connect the CAN transceiver and a second active node as described above. Configure both nodes for **125 kbit/s** and use the same CAN bus.

## 7. Expected output and hardware tests

At startup the UART should print messages similar to:

```text
STM32F091 bxCAN send/receive demo
CAN1: 125 kbit/s, standard TX ID 0x123
CAN initialized; transmitting and polling RX FIFO0
CAN TX ID=0x123 acknowledged
CAN RX ID=0x321 STD DATA DLC=2 DATA=12 AB
CAN TX ID=0x123 acknowledged
...
```

With a CAN analyzer or receiving node, verify recurring standard data frames with:

```text
Bitrate:     125 kbit/s
Identifier:  0x123 (standard 11-bit)
DLC:         8
Data:        CA 4E 00 01 DE AD BE EF
```

For an ACK test, use a second active CAN node at the same bitrate. A listen-only analyzer can display the frame but may not ACK it. Without a working transceiver, correct bus wiring, and another node that ACKs, the terminal will report `CAN TX error; check transceiver, bitrate, and ACK node`.

For a receive test, use a second active node or CAN adapter to send any standard or extended frame at 125 kbit/s. Since the example filter accepts every identifier, the UART should print the received ID, type, DLC, and data bytes. Try sending a different ID and payload (for example, standard ID `0x321`, DLC 2, data `12 AB`) and check that the printed line matches. The sender must be an active CAN participant; a listen-only adapter is not expected to ACK frames sent by this board. The software transmit interval is approximate; use observed frames rather than treating it as an exact period.

If initialization prints `CAN initialization failed`, inspect the APB1 clock assumption and bxCAN initialization handshake. If transmit errors occur, check TXD/RXD wiring, CANH/CANL polarity, transceiver enable/standby pins, common ground, matching bitrate, bus termination, and that a second active node is present. Do not troubleshoot a lack of ACK by connecting MCU pins directly to the differential bus.
